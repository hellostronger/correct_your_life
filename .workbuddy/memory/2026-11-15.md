## 持仓表溢出二次修复（2026-11-15 用户再发截图）

昨日修复不彻底：`@media(min-width:1280px)` 取消滚动容器的假设错了——
压缩后 1280~1500px 仍放不下 13 列，试算列照旧溢出卡片外（表头最后一列
是空 th，所以表头看起来是块空白、表体按钮漂在卡片外，就是用户截图）。

**根修**（static/index.html，纯静态刷新即生效）：
1. 删掉媒体查询，`.tbl-scroll{overflow-x:auto}` 常开——列永不出入卡片；
   代价是 th 吸顶失效，但其他 tab 表格全局就套 .table-scroll，sticky 本来
   就没生效过，持仓表是特例，回归一致无回退。
2. 尝试过「试算列右侧 sticky 吸附」更好用，但 sticky 列会盖住 underneath
   的「笔数」列（表格比容器宽时 sticky 是叠加不是占位），放弃。
3. 「建议操作」列**不进 wrap**：标签「持有/止损」被挤会竖排成一字长蛇；
   保持 nowrap，小字副行是 div 自成一行不受影响。
4. 顺手加了 hash 直达：/#holdings 打开即落持仓 tab（排查截图利器）。

验证：无头 Chrome 1080/1366 两档截图对比，全部列在卡片内、无错位、
标签横排。**教训：UI 改动必须真浏览器截图验收**，看 CSS 想当然会漏
sticky/媒体查询这类交互坑。

## 左右留白根因：.wrap 全局 max-width:900px（用户「放宽width不行吗」）

持仓表挤压的真正元凶是全站容器 `.wrap { max-width: 900px }`——1366 屏
两侧各 ~230px 白边，之前只压缩列宽没质疑容器。修复：宽屏逐档放宽
（1180→1100 / 1400→1340 / 1680→1580），不一刀切 100% 是防 2K 超宽屏
下文字行太长难读。无头 Chrome 1366/1920/900 三档验收：1366 起 13 列
全可见免滚动，公众号页宽屏下订阅源表格一屏放下无破版。

## 建议 vs 实际操作 统计（用户需求）

新模块 `advice_followup.py`（纯逻辑+14单测）+ `/api/advice-followup` + 持仓页统计卡。

三步链路：
1. **信号聚合**：advisory log 连续刷（1分钟一轮），同(code,action)间隔≤24h
   归并成一条信号（首行价=信号锚点，建议股数取整段最大）；hold/trend_wait 不算。
   股数语义：t_sell/t_buy→movable；trend_reduce/spike_reduce→detail.shares/
   shares_suggest；hard_stop→base_shares（清仓信号）。
2. **采纳匹配**：信号日+3自然日内同方向实盘成交（sa_trades，一笔成交只
   消费一次防双算）；窗口外/反向不算。
3. **差额**：卖向 n×(卖价−现价)、买向 n×(现价−买价)；已采纳用实际成交价，
   未采纳用信号价×建议股数（反事实）；现价 fetch_quotes，港股×0.85 折CNY。
   差额可为负=不理是对的。

真机结果（60天窗口）：27条建议照做6/未理21；已照做执行差额 +33,913；
未理若照做 +65,285（主要是 00100 异动减持2160股@180.1 → 现价152.4 的
+50,857 和 11-12 t_sell 600@181.2 的 +14,688）；全照做净差额 +99,198。
止损警示14条大多"没理是对的"（现价都回到止损线上方，负差额）——
说明止损线10%对用户偏紧，是真实洞察。

教训：请求参数 days 上限 180（防全表扫）；created_at 是 UTC 展示时要+8
（明细表目前显示 UTC 时间，trade_date 是本地日期没问题）。
